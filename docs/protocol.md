# DYNEX LAN protocol and bandwidth policy

`Dynex.Core` is a .NET 9 library without third-party packages. It discovers DYNEX instances and computes a local download policy. It does not install drivers, change Windows Firewall/router settings, or shape packets. The runtime must apply `LimitDecision.DownloadLimitMbps` and remove its automatic shaping when that value is `null`.

## Automatic LAN mode (default integration)

`AutoLanPeerService` connects DYNEX PCs automatically without a shared or hard-coded secret and without an exchanged pairing code. `IPeerService` is the common lifecycle/status API implemented by both `AutoLanPeerService` and the existing opt-in `PeerService` PSK mode. The old PSK protocol remains available; it does not interoperate with AutoLAN packets.

Generate one persistent ECDSA P-256 identity with `AutoLanIdentity.GenerateSigningKey()` and protect the resulting Base64 PKCS#8 private key in the user's DPAPI identity store. `AutoLanIdentity.GetDeviceId(privateKey)` returns a stable Guid from the first 128 bits of SHA-256 over its canonical SPKI public key. Construct `AutoLanPeerService(settings, signingPrivateKeyBase64)` with that derived `settings.DeviceId`; a mismatching ID is rejected before any socket opens. `GroupKeyBase64` is unused in this mode. Both service implementations accept trailing optional `Publish` arguments `idleBaselineMs`, `latencyTargetId`, `idleBaselineAtUtc`. A separate monotonically increasing feedback sample ID advances on `Publish`, not heartbeat transmission; unchanged heartbeats cannot masquerade as new latency measurements.

Automatic acceptance is a private-home-LAN trust policy, not pre-established device authorization. New valid cryptographic identities on the allowed LAN are automatically admitted. The public-key-derived ID prevents a device without the corresponding private key from taking over an existing ID, but cannot prove that an unknown new identity belongs to the user. A rogue new device may join under its own identity and advertise false gaming/latency information. Initial trust and malicious LAN participants cannot be eliminated without an explicit prior trust channel, user confirmation, or a shared secret. Display names are unverified labels. No claim of certified identity, trustworthy telemetry, or immunity to an initial active MITM is made. An active relay cannot decrypt a correctly completed honest-to-honest exchange, but can introduce its own newly accepted identity. Removing an automatic participant requires excluding it from the trusted LAN or using explicit PSK mode; a UI denylist is not implemented here.

### Scope and discovery

Production AutoLAN queries the Windows Network List Manager read-only and allows only active interfaces in `NLM_NETWORK_CATEGORY_PRIVATE`. Public, DomainAuthenticated and unknown profiles are excluded, as are loopback/tunnel interface types, public IPv4 addresses and prefixes outside /8 through /30. The [Microsoft Network List Manager API](https://learn.microsoft.com/en-us/windows/win32/api/netlistmgr/nf-netlistmgr-inetworkconnection-getadapterid) provides the adapter identity used to map a profile to a NIC. Query failures and an absent private network produce a visible `NetworkStatus` explanation. The application does not silently convert a Windows public network to private and never modifies the firewall. Profile policy is revalidated on each heartbeat, including a Public/Private change that keeps the same IP address. OS address-change events also refresh memberships, with subscriptions removed on stop.

Discovery transmits signed announcements through IPv4 multicast `239.255.39.74:39274` (TTL 1) **and** each eligible subnet's directed broadcast address. Subnet broadcast is a fallback for home mesh equipment that filters multicast; Wi-Fi client isolation or filtering of both methods still prevents automatic discovery. Configured `DirectPeers` may provide explicit unicast discovery, but must remain on-link to an eligible private NIC. Received IP packet information must identify an allowed local interface and a source in that interface's subnet. Source address is only a scope/routing observation, never an identity proof. VPN adapters configured as Private and exposing an Ethernet interface may still qualify if their addresses are on-link; physical topology cannot be proven from Windows profile data. `LoopbackOnly` is a deliberate isolated test mode which bypasses production profile discovery and accepts only loopback sources; tests use direct loopback endpoints.

### Signed challenge handshake and encrypted status

Each start creates a fresh ephemeral P-256 ECDH key, random 32-byte challenge and random session ID. A type-1 signed Hello advertises only the persistent public signing key, derived device ID, ephemeral exchange public key, session ID, challenge and timestamp. Names, games and telemetry are absent. A type-2 signed Ack includes the sender's same fields and the recipient's device ID, current session, challenge and ephemeral exchange public key, explicitly signing both participants' challenges and exchange keys. ECDSA P-256/SHA-256 uses fixed 64-byte IEEE P1363 signatures over the complete header plus JSON body. The receiver checks canonical P-256 SPKI encodings, key-derived identity, signature, 30-second timestamp freshness and the exact current recipient challenge/key before establishing a session. A bare Hello neither creates a visible gaming peer nor consumes a persistent session slot. An Ack replay cannot reset an established session's sequence counter or change its ephemeral public key.

The local private ECDH key and the authenticated remote public ECDH key produce the raw agreement secret through the .NET cryptographic provider. HKDF-SHA256 derives separate first-to-second and second-to-first AES-256 keys, with SHA-256 of a canonical ordered transcript as salt. The transcript includes protocol domain, both signing identities/public keys, both ephemeral keys, sessions and challenges; participant ordering uses `Guid.CompareTo`. Each participant component is separated by `|`; Guid hex and canonical Base64 fields cannot contain that delimiter. The domain-separated HKDF info labels are `DYNEX/AutoLAN/v1/first-to-second` and `DYNEX/AutoLAN/v1/second-to-first`. Mutable raw agreement secrets and traffic keys are zeroed when no longer needed. BCL ECDSA/ECDH/HKDF/AES-GCM primitives are used; the application protocol has not received an independent cryptographic audit.

Type-1/type-2 wire format: ASCII `DYNA`, version byte `1`, type byte `1` or `2`, big-endian UInt16 JSON byte length, UTF-8 JSON, 64-byte signature. JSON body fields are `DeviceId`, `SessionId`, `SigningPublicKey`, `ExchangePublicKey`, `Challenge`, `SentAtUnixMs`, optional `TargetId`, `TargetSession`, `TargetChallenge`, `TargetExchangePublicKey`.

Type-3 wire format: ASCII `DYNA`, version `1`, type `3`, sender Guid (16 bytes), recipient Guid (16), sender session Guid (16), recipient session Guid (16), positive increasing sequence Int64 (8), Unix-millisecond timestamp Int64 (8), random AES-GCM nonce (12), UInt16 ciphertext length (2), encrypted `WireAdvertisement` JSON, 16-byte GCM tag. Guid bytes follow .NET `Guid.TryWriteBytes`; integers are big endian. The entire 100-byte status header is authenticated as AES-GCM associated data. The receive key is distinct from the send key. The receiver validates sender/recipient/session bindings, authenticated metadata bounds and timestamps, then advances sequence state only after successful decryption and semantic validation. Device names, game names, downloads and baseline feedback are encrypted pairwise; cryptographic IDs, timestamps and packet timings remain observable.

All AutoLAN datagrams are capped at 2048 bytes and use a fixed 2049-byte receive buffer. The service holds at most 64 channel/peer records, 256 session/replay-history records and 128 per-source rate buckets. Handshakes are limited to 16 packets per source IP per second and total accepted traffic to 512 packets per second; source buckets expire after 30 seconds. A valid new session retires previously observed sessions of the same device for ten minutes. Peer status expires monotonically after the configured TTL (default ten seconds), while traffic keys/sequence protection survive absent peers for up to ten minutes so an old heartbeat cannot recreate gaming state. Stop clears peers immediately and erases traffic keys. Restart rotates ephemeral session/challenge material, invalidating old captured Acks and ciphertext. Existing manual PSK mode retains its own replay history and group isolation.

### AutoLAN validation boundaries

The console runner executes two independent real UDP loopback services with different persistent signing keys and **no shared key**. It checks bidirectional encrypted gaming status, independent stable identities, key/ID spoof rejection, signature validation, wrong/stale challenges, restart isolation, stale status, replay, byte-by-byte ciphertext tampering, TTL/fail-open, per-Publish feedback sample sequences and private-subnet arithmetic. A live read-only Windows profile query was also run successfully on the development PC. No physical two-PC multicast/broadcast/Wi-Fi/VPN or Windows profile-change test is implied by these checks. Native driver behavior, router congestion and actual game latency improvements require separate physical validation.

## Stable public API

- `DynexSettings`: `DeviceId`, `DeviceName`, `GroupKeyBase64`, `Port` (39274), `LoopbackOnly`, `DirectPeers`, `LineMbps` (200), `HeadroomPercent` (15), `GamingReserveMbps` (12), nullable `ManualDownloadLimitMbps`, `AdaptiveEnabled` (true), `PeerTtl` (10 s), `HeartbeatInterval` (2 s). Inputs are validated before opening sockets; settings changes require a new service/planner.
- `GroupKey.Generate()` returns a cryptographically random 32-byte Base64 group secret. Pair offline by explicitly sharing this key. The application must protect persistent storage, never log/export it with diagnostics, and preserve a stable random `DeviceId` per installation. The key is not sent over the network. Base64 is encoding, not at-rest protection.
- `PeerService(DynexSettings)`: `StartAsync(CancellationToken)`, `StopAsync()`, `Publish(bool isGaming, double? downloadMbps = null, double? latencyMs = null, double? appliedLimitMbps = null, string? game = null, bool shaperActive = false, double? idleBaselineMs = null, string? latencyTargetId = null, DateTimeOffset? idleBaselineAtUtc = null, double? uploadMbps = null)`, `Snapshot()`, `PeersChanged`, nullable `NetworkStatus`, `IDisposable`, `IAsyncDisposable`. `StartAsync` propagates bind failures and stores an explanatory transport error. `NetworkStatus == null` means no observed local socket error, not proof that another PC is reachable. Events execute on a service thread; marshal UI updates asynchronously. `Publish` updates the next periodic heartbeat. Call `StopAsync` before replacing a service; stopping immediately clears its peer snapshot.
- `PeerAdvertisement(Guid DeviceId, string DeviceName, bool IsGaming, double? DownloadMbps, double? LatencyMs, DateTimeOffset LastSeenUtc, string? Address = null, double? AppliedLimitMbps = null, string? Game = null, bool ShaperActive = false, double? IdleBaselineMs = null, string? LatencyTargetId = null, long? LatencySampleSequence = null, DateTimeOffset? IdleBaselineAtUtc = null, Guid? SessionId = null, double? UploadMbps = null)`. `LastSeenUtc` is local receive time. `Address` is diagnostic only. Advertised applied limits and shaper status describe what the sender reports as actually running, separately from desired policy. Upload is nullable; zero means measured idle and null means unknown or not supplied by an older peer.
- `ProbeStats(DateTimeOffset TimestampUtc, double? ExternalLatencyMs, double? DownloadMbps, bool IsGamingRelevant = true, string TargetId = "default")`. Supply a stable destination ID, honest relevance, and one local inbound NIC measurement. Missing metrics remain `null`; never substitute zero. Do not add overlapping NIC, VPN, router, or whole-LAN counters.
- `LimitPlanner(DynexSettings).Plan(bool localGaming, IReadOnlyList<PeerAdvertisement> peers, ProbeStats? probe = null, DateTimeOffset? now = null)` returns `LimitDecision(double? DownloadLimitMbps, string Reason, bool GamingActive, double? IdleBaselineMs, bool AdaptiveReduced)`. Call from one serialized runtime loop. The optional time argument supports deterministic policy tests.

## Manual PSK discovery, scope, and failure behavior

Production uses IPv4 UDP multicast `239.255.39.74:39274`, TTL 1, joined separately on active multicast-capable RFC1918/link-local interfaces. Tunnel and loopback interfaces are excluded. Direct private IPv4 endpoints are an explicit fallback for multicast filtering. IPv6, Internet peers, unauthenticated auto-pairing, router control, and firewall exceptions are not implemented. Discovery requires Windows/network policy to allow the UDP traffic. Wi-Fi client isolation, guest networks and multicast filtering can prevent discovery.

RFC1918/link-local filtering constrains address scope; it cannot identify the Windows Public/Private network profile or reliably recognize an Ethernet-style VPN adapter. A routed private VPN using the same address ranges may still carry unicast or multicast according to its configuration. Multicast TTL 1 bounds normal routed discovery. Public IPv4 sources are rejected even with a valid group key. `LoopbackOnly` is an explicit isolated test mode and rejects all non-loopback peers.

Heartbeats carry the gaming state, local metrics and actual shaping status every two seconds. Published upload and download measurements are sent as unknown after one peer TTL without another `Publish`; their local freshness uses a monotonic clock. Snapshot expiry uses a monotonic local clock, not remote wall-clock time. A missing peer expires after ten seconds; `Snapshot()` enforces expiry even if no receive event occurs. The planner independently filters stale snapshots, excludes the local device and deduplicates device IDs. A transport failure cannot retain automatic gaming limits indefinitely. A user-requested manual cap intentionally remains after gaming peers disappear. The host must continue its policy loop and remove its OS filter on service failure/exit; a separate elevated helper needs its own short watchdog lease to survive host crashes safely.

Windows can return UDP `ConnectionReset`/`ConnectionRefused` for an offline direct peer's port. These ICMP indications are normal absence signals and do not terminate the receive loop. Other socket failures are visible in `NetworkStatus`. The service subscribes to OS `NetworkChange.NetworkAddressChanged` while running and unsubscribes on stop. Address changes refresh multicast memberships on the next normal heartbeat, including same-address resume; no retry timer is used. A stopped/broken receive socket still requires explicit runtime restart. Actual DHCP/resume/VPN interface changes have not been physically exercised by the loopback tests.

## Manual PSK version 1 envelope

All integers are big endian. The entire datagram is at most 2048 bytes:

| Bytes | Meaning |
| --- | --- |
| 0–3 | ASCII `DYNX` |
| 4 | version `1` |
| 5–12 | first 8 bytes of HMAC-SHA256(master key, UTF-8 `DYNEX/v1/group`) |
| 13–24 | random 12-byte AES-GCM nonce |
| 25–26 | unsigned ciphertext byte length |
| next N | encrypted UTF-8 JSON advertisement |
| next 16 | AES-GCM tag |
| final 16 | first 16 bytes of HMAC-SHA256(authentication key, preceding envelope bytes) |

Encryption and authentication keys are separately derived with HMAC-SHA256(master key, UTF-8 `DYNEX/v1/encryption`) and `DYNEX/v1/authentication`. The 27-byte header is AES-GCM associated data. Group tags and authentication tags use constant-time comparison; the outer HMAC is verified before decryption or JSON parsing. Names, game, device identity and telemetry are encrypted. The stable opaque group tag and packet timing are visible to LAN observers. Ciphertext uses fresh random nonces; keys must be high-entropy generated keys, not passwords. Mutable decoded key material is zeroed on disposal. The application-owned Base64 key string remains subject to managed-runtime memory lifetime.

JSON fields are `DeviceId`, random per-service `SessionId`, positive increasing `Sequence`, `SentAtUnixMs`, `DeviceName`, `IsGaming`, nullable `DownloadMbps`, optional nullable `UploadMbps`, nullable `LatencyMs`, nullable `AppliedLimitMbps`, nullable `Game`, `ShaperActive`, optional `IdleBaselineMs`, `LatencyTargetId`, `LatencySampleSequence`, `IdleBaselineAtUtc`. Names and game labels are bounded to 80 UTF-16 code units, target IDs to 256, and metrics are finite and bounded (upload/download up to 100000 Mbps). Missing `UploadMbps` from older peers is interpreted as null. The receiver uses a fixed 2049-byte buffer, ignores oversized/truncated/invalid packets, keeps at most 64 peers and at most 256 replay entries. At capacity, new identities/sessions are dropped instead of evicting valid replay protection.

Replay protection checks the authenticated sender/session sequence and rejects duplicate/out-of-order packets. Previously observed boot sessions are retired when a new session is accepted, including after peer TTL expiry. Replay history remains for ten minutes. Authenticated sender timestamps must be within 30 seconds of receiver time; participating PCs need reasonably synchronized clocks. Expired replay records cannot make old packets valid because of that freshness bound. A previously unobserved valid packet within the freshness window is inherently indistinguishable from first delivery. As with other shared-secret group protocols, any paired group member can impersonate another identity or advertise false telemetry; an IP address is not proof of identity. The key authenticates group membership, not a separately certified device. Rotate the group key to remove a member.

## Budget and adaptive behavior

While any live DYNEX PC (including the local PC) is gaming, every participating PC computes its own share:

`max(0.1, (LineMbps × (1 − HeadroomPercent / 100) − GamingReserveMbps × GamingPCCount) / (LivePeerCount + 1))`

The divisor counts all live DYNEX PCs plus the local PC, whether each one is gaming or downloading. Gaming reserves are subtracted once per gamer. Game packets are exempt at the packet layer, but downloads on a gaming PC still receive only that PC's share of the remaining budget. With the defaults (200 Mbps line, 15% headroom, 12 Mbps reserve per gamer), one gamer plus one other PC yields 79 Mbps per PC; two gamers plus one other PC yield about 48.66 Mbps per PC; solo gaming leaves 158 Mbps for that PC's non-game traffic. No active gaming releases the automatic cap; a configured manual cap remains in effect. Capacity comes from explicit configuration; link speed is not an Internet-capacity measurement. All participants must use the same line settings for coherent allocation. Unmanaged LAN devices and PCs without a functioning shaper cannot be controlled or guaranteed a reserved share. UDP/local packet pacing cannot undo bandwidth already consumed upstream at the router.

Adaptive planning applies to the local share while any gamer is active. It prioritizes fresh timestamped gaming-peer feedback against each gaming PC's idle baseline; [adaptive.md](adaptive.md) documents the worst-gamer and recovery rules. The local external ICMP destination is also a fallback proxy when no gaming-peer baseline is valid. A locally gaming PC remains an authoritative source for its own congestion even if remote gamers report healthy latency. The local probe does not prove the actual game-server path, diagnose bufferbloat, or establish causality. Baseline acquisition requires at least five fresh valid samples spanning eight seconds while no gaming is active and local download load is below 15% of configured capacity. The lower quartile of up to 30 samples over five minutes resists occasional high-latency outliers. The local baseline expires after 30 minutes and resets when the probe target changes.

The local proxy fallback only counts distinct probe timestamps at most ten seconds old. Three consecutive samples exceeding baseline by `max(8 ms, 35%)` and local load above 75% of the current cap allow an 85% adjustment, no more often than every ten seconds, with a factor floor of 10%. In the absence of a prior gaming-peer reduction, three consecutive local samples below baseline plus `max(4 ms, 15%)` permit a gradual 10 percentage-point release. After a gaming-peer reduction, recovery requires fresh healthy samples from every currently active gaming peer; a healthy peer cannot replace another peer's missing evidence. If the local PC is also gaming, recovery additionally requires its own fresh valid local baseline and healthy probe. Local gaming does not reset the factor or remove its shared download cap. The automatic factor resets when gaming ends everywhere; an explicit manual cap remains. Invalid/missing/unrelated measurements cannot imply congestion. Tests use deterministic timestamps; no guessed polling delay influences the policy.

Run `dotnet run --project tests/Dynex.Core.Tests/Dynex.Core.Tests.csproj`. The console runner tests budget sharing, manual caps, stale peer expiry, adaptive baseline/hysteresis, authenticated packet tampering, wrong groups, payload bounds, replay/retired sessions, Unicode names, and two actual UDP services on distinct loopback ports including start/stop/restart and peer-loss release. This is a socket integration test on one PC, not a physical two-PC LAN/firewall/Wi-Fi/VPN test. Driver shaping and physical WAN latency improvements require separate runtime and device validation.

## Shared download-budget proposals

Both encrypted status protocols add the optional `BudgetProposal` object with `LineMbps`, `HeadroomPercent`, and `GamingReserveMbps`. Valid ranges match `DynexSettings`: finite capacity 1–100000 Mbps, headroom 0–90%, reserve 0–100000 Mbps. An authenticated invalid object is rejected. Omission remains compatible with legacy peers and is explicitly unknown. Services advertise their original local constructor settings while the latest runtime `Publish` is younger than peer TTL; stalled publishers omit the proposal. No new `Publish` argument is needed. Changing capacity/policy requires the existing service/planner replacement path. Never publish the negotiated minimum as a local measurement, because it would circulate a departed participant's low value indefinitely.

With `N` live unique participants including this PC and `G` gamers, every participant computes each valid original proposal's candidate `max(0, LineMbps * (1 - HeadroomPercent / 100) - G * GamingReserveMbps)` and selects the smallest candidate as `SharedDownloadBudgetMbps`. `SharedCapacityMbps` is the smallest original advertised capacity. All PCs, including gaming PCs with background downloads, receive at most `floor(pool / N * 100) / 100`; adaptive and manual limits can only reduce a share. Games and voice bypass the actual download queue separately. There is no leader, demand borrowing or idle-share redistribution.

`LimitDecision` exposes `SharedDownloadBudgetMbps`, `ParticipantCount`, `GamingCount`, `SharedCapacityMbps` and `SharedBudgetComplete`. Complete means all currently observed participants supplied valid proposals and positive shares fit the existing 0.1 Mbps backend minimum. With insufficient residual capacity the existing 0.1 Mbps best-effort cap remains, the raw pool is not inflated, and Complete is false with an explanatory reason. Legacy/missing proposals count as participants and make Complete false. No gamers means no automatic pool; explicit local manual caps remain.

The sum-of-shares bound requires converged membership/proposal views and functioning filters applying those shares. Complete alone neither proves global membership convergence nor certifies filter activity. Use `ShaperActive` and `AppliedLimitMbps` separately; old applied acknowledgements can temporarily exceed a newly reduced pool until commands converge. Network partitions, asymmetric discovery, disabled/missing filters, unmanaged LAN traffic and stale/incorrect physical-capacity estimates prevent a global enforcement guarantee. `LineMbps` is each PC's active configured estimate (normally the last speedtest), not current NIC traffic or proof of actual WAN capacity. A cold start while gaming immediately receives the static common pool; without an unloaded reference it cannot claim latency-based adaptation.

The three-client UDP test uses independent AutoLAN keys and local configurations 200/160/240 Mbps with different reserve policies. All derive a 136 Mbps pool and 45.33 Mbps shares. Publisher-confirmed simulated apply values total 135.99 Mbps, within that pool. Real encrypted UDP also exercises gamer handover, two gamers (128 Mbps pool) and departure/TTL of the 160 Mbps participant (remaining pool 158 Mbps, two shares of 79). The acknowledgements simulate successful local application; this test uses no kernel filter and proves protocol/planning coherence, not physical packet pacing or a three-PC hardware LAN.
